# 故事生成流水线 · 设计文档

2026-09-09，由与 QC 的四轮讨论定稿。

**修订（2026-09-09，r01 之后）**：第一轮 6/6 全否决，理由集中在「太日常」「寡淡」。
诊断出的根因不是措辞而是**生成单元**：原设计问的是「把这几个人放进这个房间会发生什么」，
那是个生活流问题。已被接受的六篇故事没有一篇从房间出发。因此做了三处改动，
详见 [`tools/story_pipeline/README.md`](../tools/story_pipeline/README.md)：

1. **生成单元换成四个前提模板**（后果 / 矛盾 / 放大 / 移植），全部反推自已被接受的故事。
   地点和人物由模型决定，不再预先指派——覆盖度加权被移除，它当初是生产考虑（冷门角色要有戏）
   被误当成了质量考虑，实际把每轮推向了那些从没发生过好故事的房间。
2. **`differs_from` 换成 `nearest` + `stands_beside`。** 原字段问"区别在哪"，
   模型一律用"更小、更静、更少人物"来作答——那是最便宜的差异化方式，**它本身正在制造寡淡**。
   新字段问的是"凭什么配站在那一篇旁边"，并明确禁止靠写得更小来制造区别。
3. **不再要求大纲，直接写完整短篇。** 一句话的容器奖励一句话就能装下的前提。
   同时新增 `residue` 字段（这个故事留下什么改不回去的东西），因为已被接受的每一篇都有。

一轮的规模因此从 13 变成 **17**（4 模型 × 4 个基础位 + 1 个扩展位）。

**实现状态（2026-09-09 更新）**：第 1–4 步与终端盲评已实现，见
[`tools/story_pipeline/`](../tools/story_pipeline/README.md)。Discord 推送用 webhook 已实现，成稿衔接未做。
`--dry-run` 已跑通完整回路（13 次调用 → 13 份候选 → 盲评裁决 → 揭晓 per-model 统计），
25 个单元测试全部通过。四个 adapter 代码就绪但当前均不可用：两个缺 API key，
两个 CLI 不在本机 PATH 上。

**实现状态（2026-09-10 更新）**：新增本地评审站
[`tools/story_review/`](../tools/story_review/README.md)，成为主要的评审入口（终端 `review.py` 保留，
Discord 推送不再是评审流程的一部分）。随之改动的流水线：

1. **0–10 打分决定去向**：0–3 丢弃，4–7 候补，8–10 选中；选中并写批注即「按意见重写」。
   丢弃理由改为可多选，但 QC 的批注是主要反馈，评审站上丢弃和候补都必须写批注。
2. **两种重写都回到原模型**：候补在下一轮生成时按批注重写；选中带批注的立即重写，改写稿进同一轮等 QC 批。
   改写稿不计入 per-model 统计。
3. **输出格式移到 `formats/default.json`**：QC 发现格式本身会改变模型写故事的倾向，
   所以格式要能不改代码地调整、并按版本对照。抽出时校验过渲染结果与原 brief 逐字节相同。
4. **大纲上限从固定 200 变成范围**：按位子随机，同位子四个模型共用，保住"brief 逐字节相同"。

实现时对本文档做了一处补充：**同一轮里四个模型收到的（人物组 + 场景）组合也相同**，
不是各自挑三个。理由与"brief 必须逐字节相同"是同一条——如果每个模型写的是不同的
人物和场景，就没有 like-for-like 的对照，那份相同的 brief 也就白要了。组合由脚本按
覆盖度加权指派（出场少的角色和场景权重更高），保留随机性，不做成轮值表。

## 为什么是这个形状

一句话：**四个模型并行出前提，QC 盲评裁决，Claude 统一写正文，所有裁决都留档。**

三条约束决定了其余所有取舍：

1. **QC 的注意力是唯一的稀缺资源。** 模型调用便宜，人工判断不便宜。所以每轮的产出量按"一次能看完"来定，裁决动作压到一次点击。
2. **模型身份不能在裁决时可见。** 否则两三轮后会形成偏好、开始略读，选择被污染，per-model 数据也一起废掉。
3. **被否决的东西比被选中的东西更有研究价值。** `qc-taste` 的证据体系里 `rejected` 权重最高，而现有语料里只有一条干净的否决样本（E022）。这条流水线的副产品就是把否决样本从"偶尔一条"变成"每周十几条"。

第 3 条意味着：这套流水线同时是生产工具和实验装置。两个身份不冲突，但凡有冲突时以实验的干净性优先——因为生产可以补救，被污染的数据不能。

## 一轮的生命周期

```
构建 brief ──> 12 次生成调用 (+1 扩展位, +0/4 种子位)
                      │
                      ▼
            写入候选库（含模型名，不外露）
                      │
                      ▼
            Bot 发到 Discord 单频道，只给 ID，乱序
                      │
                      ▼
            QC 用 emoji 裁决（丢弃需二次选理由）
                      │
        ┌─────────┬────┴────┬──────────┐
        ▼         ▼         ▼          ▼
      丢弃      备选      选定     选定待改
        │         │         │          │
    研究库    备选池   ──> Claude 写正文 <──
                             │
                             ▼
                    公开仓库 stories/
```

## 一、生成阶段

### 产出量

| 位 | 数量 | 说明 |
|---|---|---|
| 基线位 | 12 | 4 模型 × 3 个（人物组 + 场景）组合 × 1 条 |
| 扩展位 | 1 | 允许引入新元素的那一条，四个模型轮流承担 |
| 种子位 | 0 或 4 | QC 有 idea 时，四个模型各写一份 |

**扩展位为什么是第 13 条而不是 12 条里的一条。** QC 原方案是 12。把扩展位塞进 12 里会有两个后果：新元素出现率变成 1/12 以上（对"不鼓励"来说偏高），并且承担扩展位的那个模型当轮的基线样本少一条，per-model 对照就不对称了。做成独立的第 13 条，12 条基线保持完全对称，扩展位单独统计、不进 per-model 采纳率。审阅成本只多一条。

**种子位是最有价值的一次对照。** 同一个种子、四个模型、QC 选谁——这是能拿到的最干净的模型—taste 对齐度测量。建议即使没有新 idea 也从备选池里捞一条当种子，让它成为常设项而不是偶发项。

### brief：四个模型必须收到完全相同的字节

这是整套设计里最容易被悄悄破坏的一点。

**Claude Code 和 Codex 作为 CLI 会自动加载所在目录的 `CLAUDE.md` / `AGENTS.md`**，而 Kimi、DeepSeek 走 HTTP 只拿到你发过去的文本。如果在仓库里跑 CLI，四个模型的输入就不一样了，per-model 差异里混进了"谁看得多"这个变量。

因此：

- brief 由一个构建脚本生成，**自包含**，不依赖任何隐式上下文；
- 两个 CLI 在**干净的临时目录**里跑（无 `CLAUDE.md` / `AGENTS.md`），brief 全部经参数或 stdin 传入；
- 同一轮内四个模型收到的 brief 逐字节相同（消融分组见第五节，分组差异也必须是 brief 内容的差异，不能是加载路径的差异）。

brief 内容：

1. 12 份 bible 的压缩版（一句话 + MBTI + 核心矛盾 + 口头禅 + 道具）
2. 场景清单（`Scene Reference/` 的 12 个可用地点）
3. **每篇已有故事的一句话摘要**——用于去重，也是 `differs_from` 字段的判据
4. 记忆事件与番外剧场的区分规则
5. 客串角色清单（见第四节，复用是鼓励项，必须让模型知道有哪些可复用）
6. taste profile —— 按消融分组给或不给

brief 构建脚本是整套东西里工作量最大的一块，**比调模型难**。它的输入就是仓库里已有的 `character reference/`、`stories/`、`Scene Reference/`，和 `sync-content.mjs` 读的是同一批源。

### 四个模型怎么调

```
Kimi     → HTTP，OpenAI 兼容端点
DeepSeek → HTTP，OpenAI 兼容端点
Claude   → 子进程，Claude Code 的非交互模式
Codex    → 子进程，Codex CLI 的非交互模式
```

上层只认一个签名：

```python
def generate(brief: str) -> str: ...
```

HTTP 那两个共用一份 OpenAI SDK 代码，只换 `base_url` 和 key。CLI 那两个各包一个 `subprocess.run`。**不需要手动给 Codex 输入。**

> 实现前先各跑一次 `codex --help` / `claude --help` 确认当前的非交互子命令与参数，两个 CLI 迭代都很快。

**按 (模型 × 组合) 拆成 12 次独立调用，每次要 1 条。** 不要让一个模型一次吐 3 条：一次超时会丢 3 条，而且模型会倾向于让同一批内部互相差异化，反而收窄了单条的取值范围。

HTTP 两个可并发；CLI 两个串行，每次要启动 agent 循环，单次几十秒属正常。整轮预算几分钟。

### 输出格式

要求 JSON。HTTP 两个可用 `response_format={"type":"json_object"}` 强制；两个 CLI 不保证，可能在 JSON 前后加一句寒暄。**解析器必须容错**：抓第一个 `[` 到最后一个 `]`，失败就整段留存并标记 `parse_failed`，绝不让一次格式抖动搞崩整轮。

每条大纲的字段：

| 字段 | 内容 |
|---|---|
| `hook` | 一句话前提 |
| `turn` | 一句话转折 |
| `differs_from` | 这条与哪篇已有故事最接近，区别在哪 |
| `cast` | 出场角色 |
| `location` | 场景 |
| `new_elements` | `none`，或新元素清单 + 每项一行必要性说明 |

`differs_from` 是强制字段，作用是逼模型自己先做一次去重，也让 QC 一眼看出是不是又一个变形的《七天追咬》。

## 二、审阅阶段

### 盲评

单频道、乱序、**只显示随机 ID，不显示模型名**。模型名写进候选库文件，Bot 从不读它。裁决完成后才揭晓。

事后照样能统计每个模型的采纳率——但那个数字这时候才是干净的。

### webhook，不做 bot（2026-09-09 改定）

原方案是升级成 bot、用 emoji reaction 收裁决。**已放弃。** 现在只用 incoming webhook 单向推送：`tools/story_pipeline/publish.py` 把每轮故事发进评审频道，**一篇一帖**；裁决回到终端用 `review.py`。

这是一次自觉的降级，代价要说清楚：**webhook 只写不读，裁决收不回来**，于是读在 Discord、判在终端，需要把 id 带过去。换来的是少一个要建也要维护的组件。为压低这个摩擦，每轮第一条消息直接附上可复制的裁决命令，每篇 footer 带 id。

排版按 Discord 的硬限制来：一条消息 2000 字符、embed description 4096、embed field 1024。所以每篇是**一个元数据 embed**（标题、类型、地点、长度、出场、前提、比照、残留、新元素）**加上按空行切分的若干条正文消息**，记忆事件与番外用不同颜色。

**embed 里不出现模型名**——盲评在这里同样成立。`slot` 会显示，因为它说明这篇被要求写成什么，属于公平阅读的一部分。

### 四类裁决

在终端执行。`review.py` 强制两条：丢弃必须带理由；`--stats` 在还有 pending 时拒绝揭晓模型。

| 命令 | 去向 |
|---|---|
| `discard --reason X` | 丢弃 → 研究库 |
| `shortlist` | 备选池 |
| `select` | 选定 |
| `revise --notes "..."` | 选定待改 |

理由集见 `store.REASONS`，r01 之后按 QC 的实际用词重写过一次。

**理由是强制的。** 没有理由的废稿，半年后 QC 自己也说不出当初为什么不要——研究库就变成一片坟场。带标签的否决样本才是这条流水线对 `qc-taste` 最大的贡献。

## 三、四类去向与状态机

```
生成 ──> pending ──┬── 🗑️ ──> discarded  （终态，进研究库，带 reason）
                   ├── 📥 ──> shortlisted（可被后续轮次捞出）
                   ├── ✅ ──> selected ──> drafting ──> published
                   └── ✏️ ──> selected_with_notes ──> drafting ──> published
```

### 备选池的衰减规则

不设上限的备选池会变成垃圾填埋场：只增不减，第十轮时面对的是一堆"当初不够好、现在也还是不够好"的存货。

- 每条备选记 `revisit_count`
- 每轮最多从池中捞 1–2 条（作为种子位输入，或重写后重新参评）
- **捞满 3 次仍未选定的自动降级为 discarded**，理由记 `备选三次未选中`

这个降级动作本身也是数据：它标出哪一类点子总是差一口气。

## 四、新人物与新地点

QC 的立场是**不鼓励但不禁止**，并担心提示词里的抑制性措辞会让模型完全不敢生成。这个担心有明确机制：「你可以加但要慎重」是一个道义框架，模型在这种框架下稳定选安全侧——不加就永远不会被质疑。四个模型看同一句话，抑制还是相关的，会得到四个 0。

三层处理，全部采用：

### 结构：抑制性措辞只出现在扩展位

12 条基线的 brief 里**完全不提**新元素的许可问题，只在 `new_elements` 字段的说明里中性地要求填写。扩展位用**独立的提示词**，明确要求"写一个必须引入临时客串角色或新场景才能成立的故事"。

这样那句带抑制性的话根本不进入另外 12 次调用的上下文，污染不到它们。这是 QC 那个担心的直接解法。

### 措辞：填字段，不是请求许可

任何位置都不要写"你可以……如果必要的话"。改成强制输出 `new_elements` 字段，值是 `none` 或清单。**填字段是中性动作，请求许可不是。** 同一件事换个语法位置，抑制效应显著更小。

### 分档：三档，不是一条规则

新人物和新地点的成本差一个量级，不该合并成同一条规则。

| 档 | 政策 | 说明 |
|---|---|---|
| **复用已有客串** | **鼓励，无需说明** | `_guests/` 里已有 haide-human、mimi 的姐姐、QC 的三个女伴。素材现成，是白给的连续性 |
| **新客串角色** | 扩展位内允许，一行必要性说明 | 已有 `_guests/` 目录与 T014（无眼、低复杂度）兜底，成本低 |
| **新地点** | 单独提案，不随故事大纲提出 | 要出 Scene Reference 图、进 `characters.config.mjs`、配中英名、生成地点页。这是生产工作，应与故事裁决分开 |

第一档在 QC 的原方案里没有，但它应该是默认优先项——brief 必须带客串角色清单，否则模型不知道有什么可复用。

### 验证：记数，不猜

每轮统计每个模型的客串 / 新地点出现率。**连续三轮为 0 说明措辞没生效，换方案**，不要靠感觉判断提示词有没有用。

## 五、消融分组

`ResearchAssets/experiments/` 里本就列了"种子消融"。这条流水线天然适合：

- 部分轮次把 taste profile 放进 brief，部分不放
- 比较两组的采纳率（✅ 与 ✏️ 合计 / 总数）

如果带 taste 的组采纳率显著更高，就得到了一个**关于"创作者 taste 可被提取并迁移"的定量结果，且不需要 user study**。这可能是整套东西里研究价值最高的一块，代价只是分组和记录。

每条候选记 `taste_context: on | off`。分组按轮次而非按模型，否则和 per-model 对照混淆。

## 六、成稿阶段

选定的大纲交给 **Claude 统一写正文**。四个模型负责前提的多样性，成稿声音保持一致。

**取舍要说清楚**：这意味着研究主张收窄为"模型在**前提生成**上的分歧"，而不是"在创作上的分歧"。T007（克制、短对话、延迟反应、不解释的结尾）是一套很具体的文风，让四个模型各自逼近它只会得到四种都不太对的腔调。这个收窄是自愿的、有理由的，写论文时要如实说明。

**写正文的那次调用不带 `model` 字段。** 盲评保护 QC 的判断，这一条保护成稿——否则 Claude 可能对"自己的"点子更宽容。

成稿后走现有流程：写入 `stories/`，`sync-content.mjs` 同步，`story_added.py` hook 询问是否回写 bible，`translate-en` 出英文版，部署，`discord-notify` 通知。

## 七、数据落在哪

**不上数据库。** 一条候选一个 md，带 frontmatter，可 grep、可 diff、可被脚本直接读，也不引入这个项目里唯一一个不透明的二进制。

```
ResearchAssets/story-candidates/          ← 私有：候选、裁决、否决理由
  2026-09-16-r01/
    c-a7f3.md
    c-b1e9.md
    ...
    round.json                            ← 轮次元数据、消融分组、brief 的 sha256
```

为什么在私有子模块：里面是 QC 对朋友虚拟分身的原始否决理由。**选定并写完的故事才毕业到公开仓库的 `stories/`。**

frontmatter：

```yaml
id: c-a7f3
round: 1
slot: baseline | expansion | seed
model: deepseek                  # Bot 从不读这个字段
taste_context: on | off
cast: [haide, mushi]
location: ArtClassRoom
new_elements: none
verdict: pending | discarded | shortlisted | selected | selected_with_notes
reason: null                     # 丢弃时必填
notes: null                      # ✏️ 时的修改建议
revisit_count: 0
decided_at: null
```

密钥沿用现有位置：Kimi / DeepSeek token 进根目录 `.env`（已 gitignore），Discord webhook 进 `ResearchAssets/config/story-pipeline.env`（评审频道，与 `notify.env` 的公开通知分开）。两个 CLI 不需要 key，用已登录的订阅态。

## 八、每轮记什么

`round.json` 至少记：

- 每个模型的四类裁决分布（采纳率 = ✅+✏️ / 总数）
- 客串出现率、新地点提案数
- 消融分组
- 从备选池捞出的条目及其 `revisit_count`
- brief 的 sha256（保证"同一轮四模型同输入"可事后验证）
- 生成失败 / `parse_failed` 计数

## 九、成本现实

Codex 与 Claude 走订阅，不额外花钱，但**有速率限制，批量自动化会撞上**。每轮 6 次 CLI 调用大概率没问题；要加频次或加组合数，先撞墙的一定是这两个。

由此有一个待定取舍：**是否买一个 OpenAI API key，把 Codex 也变成 HTTP adapter。**

- 留 CLI：不额外花钱，但多两条代码路径、慢、受限流、还要维护"干净目录"这个约束
- 换 HTTP：四个 adapter 完全同构，brief 注入路径唯一，一轮几秒跑完，代价是按 token 计费

**建议先按 CLI 跑通两三轮**，把 brief 和裁决闭环调顺；届时若仍想继续且限流碍事，再换。不要为一个还没验证的流程预先付费。

## 十、待定

1. **轮次节奏。** 建议每周一轮，把审阅当成一次 20 分钟的固定动作。日更会淹死人。
2. **组合怎么选。** 三个（人物组 + 场景）组合是模型自选，还是脚本按覆盖度指派（比如优先派出场次数最少的角色）？自选省事但会集中在好写的角色身上；指派能保证冷门角色也有戏。倾向指派，但需要先跑一轮看模型自选的分布再决定。
3. **理由集是否够用。** 6 个标签是拍脑袋定的，跑三轮后看分布：如果 60% 都落在"就是不好笑"，说明标签太粗，要拆。
4. **扩展位轮换是否公平。** 四个模型轮流，四轮才走完一圈。若中途改变模型组合，轮换表要重置。

## 实现顺序建议

先做能验证假设的最小闭环，不要一次做完：

1. brief 构建脚本（最难，且其余一切依赖它）
2. 两个 HTTP adapter —— 先只用 Kimi + DeepSeek 跑通生成与落盘
3. 候选库格式与状态机（纯文件操作，无外部依赖）
4. 两个 CLI adapter
5. Discord 推送（webhook 单向；裁决留在终端）
6. 成稿衔接与统计

第 1–3 步做完就已经能手动跑一轮了。第 5 步最终没有做成 bot：跑过两轮之后判断，收裁决的那半边不值得为它维护一个 bot，读稿这半边一个 webhook 就够。
